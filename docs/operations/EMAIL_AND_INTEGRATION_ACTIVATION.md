# Email and integration activation

This runbook turns the verified release candidate into a connected installation.
It does not grant permission to enter live client data. Complete synthetic tests
and record evidence in `/settings/launch` first.

## 1. First administrator

1. Generate a unique high-entropy value of at least 32 characters in the approved
   secret manager.
2. Set `INITIAL_ADMIN_SETUP_TOKEN` in the deployment environment and restart only
   the application container.
3. Open `/setup`, create the named administrator, then sign in normally.
4. Remove `INITIAL_ADMIN_SETUP_TOKEN` and restart the application.
5. Confirm `/setup` reports that initial setup is complete.

Do not put the token in a support message, screenshot, issue, audit note, or Git.

## 2. Account invitation and recovery

### Local development

Supabase captures Auth invitation and recovery mail in Mailpit. Open
`http://127.0.0.1:54324` after requesting an invitation or recovery message. This
mail never leaves the development machine.

Mailpit is not the application Inbox. The application Inbox contains ingested
charter-operation email; Mailpit is only a development mailbox for Auth mail.

### Production

Choose one account-access delivery mode:

* **Manual links (recommended for the low-cost private pilot):** set
  `AUTH_MANUAL_LINKS_ENABLED=true`. An administrator generates a Supabase
  single-use invitation or recovery link in **Settings > Users**, copies it,
  and sends it to the intended person through a secure channel. The link is
  displayed only in the response and is never stored or logged by the app. The
  app stores only an encrypted Supabase verification hash behind its own
  one-time, 24-hour confirmation hand-off, so mail-client previews cannot spend
  the code before the invited person explicitly confirms on their device.
* **SMTP:** configure SMTP in the approved hosted Supabase Auth project or
  self-hosted GoTrue deployment. Keep credentials in provider/deployment secret
  storage, not in the web interface. Test both a staff invitation and password
  recovery, then set `AUTH_SMTP_CONFIGURED=true`.

Do not enable both modes unless there is an operational reason. A manual link is
the one-time tokenised action URL generated by Supabase; the application does
not invent or persist its own invitation codes.

## 3. Gmail ingestion

1. Create the client-owned Google Cloud project and OAuth consent configuration.
2. Grant the reviewed application only the Gmail read/modify and compose scopes
   used by the connection screen. Do not grant automatic send authority.
3. An invited staff member connects the operational account under **Settings >
   Account and alerts > Google Workspace**.
4. An administrator opens **Settings > Connections**, chooses that account under
   **Gmail > Incoming mail**, and enables monitoring. The first automation tick
   records the current Gmail history cursor without importing older mail.
5. Keep the application-owned scheduler inactive until the synthetic route is
   accepted. Local n8n is optional for rehearsal only and never needs a Gmail
   credential.
6. Run a synthetic set: new enquiry, follow-up, internal message, circular, and
   unrecognised message.
7. Verify classification, human review, Telegram/in-app alert materialisation,
   draft behaviour, idempotency, and failure visibility.
8. Enable the application-owned scheduler. Google and Telegram work remains
   inside the application-owned adapters; no scheduler holds provider credentials.

The app cannot create a Google Cloud project or consent screen on the operator's
behalf. That boundary is intentional.

## 4. Personal Google Workspace connections

1. In the client-owned Google Cloud project, create one Web OAuth application.
2. Add the exact callback URL
   `https://<approved-app-host>/api/integrations/google/callback` (or the local
   `http://localhost:3000/...` equivalent) to Google&apos;s authorised redirect URIs.
3. Store `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` only in
   deployment secret storage, then restart the application.
4. Each employee opens **Settings > Account and alerts** and selects
   **Connect Google Workspace**. Google, not Torrance Yachts, presents the consent
   screen.
5. Confirm the connected account appears in Settings and complete a synthetic
   internal alert before enabling the email route.

The app encrypts ongoing access in Supabase Vault and never shows a refresh token
or client secret in the interface. The granted scope permits approved inbox
routing and controlled Gmail drafts; external recipient operations do not send
mail automatically.

### Other mail providers

Staff who do not use Google can connect a TLS IMAP mailbox in **Settings >
Account and alerts > Other mailboxes**. The screen includes iCloud, Outlook /
Microsoft 365, Yahoo and Zoho presets. It accepts a provider-issued app password
only; it never accepts or stores a normal mailbox password. IMAP messages follow
the same private-by-owner ingestion boundary as Gmail. Microsoft 365 OAuth is
not implemented; where the organisation disallows IMAP app passwords, use the
approved Google route or defer that mailbox until Microsoft OAuth is added.

## 5. Telegram

1. Create one company-controlled bot with BotFather.
2. Store `TELEGRAM_BOT_TOKEN` only in deployment secret storage.
3. Set the non-secret bot username as `TELEGRAM_BOT_USERNAME` and create a
   high-entropy `TELEGRAM_WEBHOOK_SECRET` in deployment secret storage.
4. Register `https://<approved-app-host>/api/integrations/telegram/webhook` as
   the Telegram webhook with that same secret token. The endpoint must be HTTPS
   and must not be exposed through an untrusted proxy.
5. Enable the Telegram integration record.
6. Each staff member opens **Settings -> Your alerts and connections** and
   selects **Connect Telegram**, then presses Start in the company bot. The
   manual chat-ID field is only a documented recovery fallback.
7. Send a synthetic internal alert and verify pairing, delivery, and failure
   history. Confirm that a reused pairing link is ignored.

Telegram delivers concise internal alerts with a **Review in workspace** button.
The button opens an authenticated application page; it does not approve, send, or
change anything in Telegram. For a new enquiry, staff review the AI extraction,
route the message as an enquiry, then select **Create Gmail draft**. The draft is
created in that staff member's connected Gmail account and is never sent by the
application. Broker, captain, booking, invoice, and status communications remain
reviewable even when Telegram is connected.

## 6. Background scheduler

The hosted application-owned worker runs inside the private Compose network and
uses only the application automation secret. Enable it only after the synthetic
acceptance path is recorded. Local n8n is retained for development rehearsal;
it is not deployed as a production scheduler and never stores Google or Telegram
credentials. PostgreSQL and application commands remain authoritative.

## 7. AI

Development uses the deterministic local provider. Production may use the
approved OpenAI provider by setting `AI_PROVIDER=openai`, `OPENAI_API_KEY`, and
the reviewed model in server-only configuration. Confirm the data policy before
sending email or contract text. Identity documents are excluded. AI output is a
suggestion and never books a yacht, sends consequential communications, or
changes authoritative workflow state.

Alternatively, an individual staff member may use **Torrance Local AI** from
their AI settings. They install Ollama on their Mac, pair the helper with a
short-lived code, and select a local model. The helper polls outward over HTTPS;
the hosted service never reaches a MacBook or exposes its Ollama endpoint.
`qwen3:4b-instruct` is the default recommendation for this workflow. A signed
macOS helper installer is a later distribution task; the initial helper is a
reviewed local script.

## 8. Yachtfolio

Yachtfolio booked dates remain a manual named task because this project has no
approved Yachtfolio write API. The user completes the external action, supplies a
reason/evidence, and records completion in the booking. Reopening is also audited.
This is complete functionality, not a disconnected automation placeholder.

## 9. Acceptance evidence

Use `/settings/activation` for live configuration/health indicators and
`/settings/launch` for formal evidence and sign-off. Never mark a check passed
solely because a credential exists; verify the complete synthetic path and its
failure handling.
