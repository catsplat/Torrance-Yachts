# Case study: from dashboard concept to secured operational data

## Challenge

The original concept was a private dashboard that could eventually coordinate yacht enquiries, bookings, tasks, documents, notifications, and booked dates. The first foundation release proved the interface but deliberately held synthetic static data. The next risk was not visual: it was proving that an internal user and a business record could move safely through the complete application stack.

## Delivered slice

The Phase 2 slice lets an authenticated internal employee list, create, inspect, and edit yacht records. It captures specifications, operational status, preferred ports, and a per-yacht phone for future notification routing. Every successful change is attributed and audited.

The work combined:

- Next.js server rendering, server actions, and responsive React forms;
- Supabase authentication and local development tooling;
- PostgreSQL schema design, constraints, privileges, Row Level Security, and triggers;
- Zod boundary validation and Vitest unit tests;
- pgTAP permission tests that impersonate anonymous, staff, inactive, and administrator contexts;
- CI, architecture decisions, setup instructions, audit evidence, and a development diary.

## Engineering decisions

The database—not the page—enforces authorisation. This means a future n8n workflow or API receives the same protection as the current interface. Audit events are generated by triggers for the same reason.

The implementation avoids a manually editable yacht-availability flag. The final product must derive availability from bookings and the specified operational buffer; introducing duplicate state during an early slice would create future reconciliation bugs.

The service was built local-first. This allowed security behaviour, destructive resets, and migrations to be tested without exposing live data or committing production credentials.

## Verification

The release candidate passed lint, strict type checks, a production build, three validation tests, fourteen database permission tests, schema linting, and a zero-vulnerability dependency audit. A browser acceptance pass covered authentication, protected routing, create/edit behaviour, audit growth, sign-out, and mobile navigation.

## Skills demonstrated

- translating a hand-drawn operational workflow into durable domain boundaries;
- selecting managed components to minimise security-sensitive custom code;
- building security and auditability before business data is introduced;
- distinguishing operational yacht status from booking-derived availability;
- producing reproducible engineering and audit documentation alongside implementation.

All examples and verification records use synthetic data. No private client, captain, contract, KYC, bank, rate, or credential information is included.
